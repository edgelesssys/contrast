# RFC 015: HTTP API Security

## Background

[RFC 014](014-backwards-compatibility.md) defines how the HTTP API is versioned and negotiated, and explicitly defers the design of the API's security mechanisms to this RFC.

Under gRPC/aTLS, authentication in both directions is a side effect of the transport handshake.
The Coordinator authenticates itself by embedding an attestation report in its TLS certificate, and the client authenticates itself by presenting a TLS client certificate whose key is either an owner key or is bound into the client's own attestation report.
Once the transport no longer carries trust, both directions have to be reconstructed at the application level, in the request and response bodies.

Three cases need to be covered.

1. The Coordinator authenticates itself to a client (`POST /v1/attest`, see [RFC 012](012-application-level-verification.md)).
2. A client authenticates itself to the Coordinator (User API, `POST /v1/manifest`, `POST /v1/recover`).
3. A client authenticates itself to the Coordinator (Mesh API, `POST /v1/mesh/cert`).

## Requirements

Following the structure of [RFC 012](012-application-level-verification.md), the HTTP API must uphold the guarantees aTLS gives today.

1. The mechanisms must be usable over plain HTTP, with TLS terminated by an arbitrary party (the component itself, a TLS-intercepting proxy,...).
2. For each request, the guarantees of the corresponding gRPC method must be preserved:
   1. Freshness: a response, or an authenticated request, must be bound to *this specific* exchange.
   2. Authenticity: the Coordinator must be identifiable as one allowed by the expected manifest.
   3. Confidentiality: secrets must be readable only by their intended recipient, independent of the transport.
   4. Authorization: privileged requests must be provably issued by a party the manifest permits.
3. Server-side state must be optional for correctness. Losing it (restart, second replica, or a load balancer moving a client) may cost a retry, but must not cause a security or correctness failure.
4. The wire contract must live in the `apitypes` package and be versioned per [RFC 014](014-backwards-compatibility.md).

## Design

### Case 1: Coordinator authenticates itself to a client

This is largely solved already by [RFC 012](012-application-level-verification.md)'s `POST /attest`.
The client generates a 32-byte random nonce and sends it.
The Coordinator returns a TEE report whose `REPORTDATA` covers that nonce along with digests of the state being reported.
The Coordinator continues to authenticate itself solely through the TEE signature over that report.

This direction is amended by the inclusion of an ephemeral HPKE public key generated by the Coordinator, returned in the response and covered by the report data:

```
reportData = sha256("contrast attest v1" || nonce || status || transitionHash || sha256(rootCA) || sha256(meshCA) || hpkePubKey)
```

A client that validates the report therefore holds an authenticated public key it can encrypt to.
This is the replacement mechanism for aTLS binding the TLS key into the report, and is what allows us to fulfill requirement 2.iii for requests sending secrets to the Coordinator.

The key is generated ephemerally per exchange.
A fresh report is minted on every call regardless, since the client's nonce is in it, so per-exchange generation introduces little extra attestation cost.
The Coordinator holds the private key in a two minutes TTL-bounded, size-bounded pending-key cache until the follow-up request arrives.
Per requirement 4, losing this cache is benign.
The follow-up request fails with a distinguishable error and the client repeats the exchange.

For the algorithmic primitives, [HPKE](https://www.rfc-editor.org/rfc/rfc9180.html) base mode with the post-quantum hybrid KEM `MLKEM768-X25519` from [`draft-ietf-hpke-pq`](https://datatracker.ietf.org/doc/draft-ietf-hpke-pq/), `HKDF-SHA256`, and `AES-256-GCM` is chosen.
An implementation exists in [`crypto/hpke`](https://pkg.go.dev/crypto/hpke).

Note that the key isn't bound to Coordinator state.
Therefore a Coordinator awaiting recovery can still issue one, which is what [`POST /v1/recover`](#post-v1recover-recover) depends on.
The Coordinator doesn't prove possession of the private key, see [Proof of possession](#proof-of-possession) for the reasoning.

### Case 2: Client authenticates itself to the Coordinator (User API)

The request body carries an owner key signature.
If the signature can be verified against the key list in the manifest, this serves as authorization.
This replaces the `validatePeer` mTLS client certificate check.

Manifest updates reuse the existing signature scheme.
`validateSignature` already verifies an ECDSA signature by a `WorkloadOwnerPubKeys` entry over the transition hash.

Recovery has no such scheme to reuse.
Seed share owners authenticate currently by presenting their key as an mTLS client certificate, which `validatePeer` compares against `SeedshareOwnerPubKeys`.
Because seed share owner keys are RSA-4096 (while workload owner keys are ECDSA P-384), the manifest-update scheme can't be copied directly.
The new signature should instead be [RSA-PSS](https://www.rfc-editor.org/rfc/rfc8017.html#section-8.1) with SHA-256.

#### Setting the initial manifest

Currently setting the initial manifest requires no authentication of the client to the Coordinator, following the trust-on-first-use model of [RFC 002](002-secure-set-manifest-endpoint.md).
The Coordinator trusts the first manifest it's given, and the client then verifies, among everything else, that the manifest now in force is the one it set.
An attacker who races the legitimate client and sets a manifest first causes that verification to fail.

### Case 3: Client authenticates itself to the Coordinator (Mesh API)

Here the freshness requirement is reversed.
The Coordinator needs assurance that the initializer's evidence is fresh, so the Coordinator must supply the nonce.
Since the initializer is still required to, well, initialize the exchange, this costs a round trip.

```
POST /v1/mesh/cert                    (no Authorization header)
-> 401 Unauthorized
  WWW-Authenticate: contrast-attestation-v1 nonce="<base64>"

POST /v1/mesh/cert                    (evidence in body)
  Authorization: contrast-attestation-v1 nonce="<base64>"
-> 200 OK
```

This reuses the standard [`WWW-Authenticate`](https://www.rfc-editor.org/rfc/rfc9110.html#name-www-authenticate) and [`Authorization`](https://www.rfc-editor.org/rfc/rfc9110.html#name-authorization) header semantics with a Contrast-specific authentication scheme, so intermediaries treat the exchange as ordinary HTTP authentication.
The `Authorization` header only echoes the nonce.
The evidence itself goes into the request body, since servers and intermediaries limit header sizes, commonly to a few KiB, and a report with its certificate chain can exceed that.

The Coordinator holds issued nonces in a TTL-bounded, size-bounded nonce cache.
Per requirement 4, losing the cache is benign. The retry fails with `401` and the client starts over.
This is the same state-handling pattern as the pending HPKE keys, and the two caches can share an implementation.

The client's report binds two client keys to the challenge:

```
reportData = sha512("contrast mesh cert v1" || nonce || certPubKey || kemPubKey)
```

`certPubKey` is the ECDSA key the issued certificate will attest, and `kemPubKey` is an `MLKEM768-X25519` key used only to receive the sealed response.
The aTLS path uses one key for both roles, but separating avoids using one key across two cryptographic purposes.
The initializer doesn't prove possession of `certPubKey`, see [Proof of possession](#proof-of-possession) for the reasoning.

The Coordinator validates the evidence against the manifest as `stateguard.Credentials` does today.

However, we need to slightly revise SAN handling.
The current implementation appends the observed peer address to the certificate's DNS names:

```go
if host, _, err := net.SplitHostPort(p.Addr.String()); err == nil {
    dnsNames = append(dnsNames, host)
}
```

Using `X-Forwarded-For` would make certificate contents attacker-influenced, so the HTTP path should drop source-derived SANs and use only the manifest-declared ones.

### Endpoints

#### `POST /v1/attest` (GetManifests)

Attestation responses gain the ephemeral HPKE public key and the Coordinator's status.

```go
type AttestationRequestV1 struct {
    Nonce []byte `json:"nonce"`
}

type AttestationResponseV1 struct {
    Version           string                `json:"version"`
    RawAttestationDoc []byte                `json:"raw_attestation_doc"`
    AttestationType   asn1.ObjectIdentifier `json:"attestation_type"`
    // Status is one of "uninitialized", "active", or "stale".
    Status string `json:"status"`
    // HPKEPubKey is an MLKEM768-X25519 public key valid only briefly and only for this exchange.
    HPKEPubKey []byte `json:"hpke_pub_key"`

    CoordinatorState
}
```

The released `POST /attest` fails with `412` both when no manifest is set and when the Coordinator awaits recovery.
`/v1/attest` instead answers in both cases, with an empty `CoordinatorState`, and `Status` tells them apart.

The released `POST /attest` keeps its current report data construction unchanged, the new fields are only added under `/v1/`.
Security is unchanged. The added key and `Status`, encoded as a single byte, are covered by `reportData`, meaning they inherit the existing freshness and authenticity guarantees.


#### `POST /v1/manifest` (SetManifest)

The body carries the manifest, the policies, the previous transition hash, and a workload owner signature, using the existing scheme unchanged:

```
h  = Transition{ManifestHash: sha256(manifest), PreviousTransitionHash: prev}.Digest()
h' = sha256(hex(h))
sig = ECDSA-Sign(workloadOwnerKey, h')
```

The initial manifest requires no signature.
The client confirms the result with a follow-up `/v1/attest`.

The mTLS peer-key path (`validatePeer` against `WorkloadOwnerPubKeys`) is dropped, meaning the signature becomes the only authorization mechanism for updates.
The gRPC path accepts either today, so this doesn't introduce a new mechanism.
The Coordinator is no longer attested during the call, verification moves to the set-then-verify sequence the CLI effectively performs anyway.

Security is unchanged for updates.

#### `POST /v1/recover` (Recover)

This requires two requests.

1. `POST /v1/attest` with a fresh nonce, to obtain the attested HPKE public key.
2. `POST /v1/recover` carrying the seed and salt sealed to that key, plus a seed share owner signature.

The client checks that `Status` is `"stale"` and consumes only the HPKE key, as `CoordinatorState` is empty.

```go
type RecoverRequestV1 struct {
    // Nonce from step 1, identifying which pending key to unseal with.
    Nonce []byte `json:"nonce"`
    // {seed, salt} sealed to the Coordinator's HPKE key, as returned by hpke.Seal.
    Ciphertext []byte `json:"ciphertext"`
    // RSA-PSS-SHA256 over sha256("contrast recover v1" || nonce || hpkePubKey || force || ciphertext).
    Signature []byte `json:"signature"`
    Force     bool   `json:"force"`
}
```

Sealing to an HPKE key generates a fresh key pair on the client side and derives the AEAD key from it and the Coordinator's public key.
The Coordinator needs the client's ephemeral public key to derive the same secret, so that value is encoded together with the ciphertext.
The one-shot API in `crypto/hpke` concatenates the two, `Seal` returning the encapsulated key followed by the ciphertext and `Open` expecting the same.

The exchange is bound into the seal itself by passing `"contrast recover v1" || nonce` as HPKE `info`, so a ciphertext lifted into a different exchange fails to decrypt rather than merely failing a signature check.
The signature covers the Coordinator's HPKE public key, the `Force` flag, and the ciphertext, so an intermediary can't set `Force` to skip the Coordinator's sanity checks.
The response is empty, as today.
Success is confirmed by a follow-up `/v1/attest`.

Security is unchanged.
The seed is readable only by a Coordinator that produced a valid report over the HPKE key in response to this client's nonce.

## Out of scope

- Coordinator-to-Coordinator traffic, in particular `meshapi.Recover` as used by `peerrecovery`, keeps using aTLS, per [RFC 014](014-backwards-compatibility.md).
- The transit engine API, which is already HTTP-only and has an authentication model of its own.
- Hardening the trust-on-first-use on the initial `SetManifest`, as established in [RFC 002](002-secure-set-manifest-endpoint.md).

## Alternatives considered

### Proof of possession

Neither the Coordinator's HPKE key nor the initializer's `certPubKey` comes with a proof of possession, as it's unclear what one would add against the threat model:

- An attacker who substitutes a key of their own needs a TEE report over that key that validates against the reference values, which only a genuine Coordinator or initializer can produce.
- An attacker who relays honestly passes through the genuine key, so anything sealed to it stays unreadable to them, and a certificate issued for that key is unusable to them.
- An attacker who replays an older report fails the nonce check.
- A key bound into the report but not held by its producer could only be placed there by a malicious workload, which measurements are what exclude.

If an explicit confirmation is wanted anyway, a separate ephemeral signing key could be covered by the same report data, and the Coordinator could sign the response with it.
Signing with the KEM key itself isn't an option, as an ML-KEM key can't sign.
It's also unclear how possession of a post-quantum hybrid key would be proven, as ML-DSA isn't part of the Go standard library.

For certificate enrollment, [`draft-reddy-rats-key-binding-02`](https://datatracker.ietf.org/doc/html/draft-reddy-rats-key-binding-02) describes a protocol-level proof of possession, but it builds on EAT structures Contrast doesn't implement.

### Deriving freshness from a rotating server key instead of a per-request nonce

The Coordinator would hold a key for a rotation window and clients would bind evidence to its key ID.
This removes the Coordinator-side caching, the Mesh API round trip, and lets a client reuse one report across many requests, but it weakens freshness from per-request to per-window.

### Stateless challenges

Instead of a nonce cache, the Coordinator could issue `nonce = HMAC(k, expiry) || expiry` and verify without state.
This removes the cache, but not the need for a replay cache within the validity window
However, this might make sense if the nonce cache becomes an issue in multi-Coordinator deployments.
